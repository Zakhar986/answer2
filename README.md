1. SSH на 127.0.0.1 и правило ACCEPT для порта 22
Снаружи к SSH никто не подключится. Пакет на 203.0.113.10:22 пройдёт firewall, потому что правило ACCEPT его пропустит. Дальше ядро ищет сокет, который слушает 203.0.113.10:22 или 0.0.0.0:22, и не находит его. Есть только сокет на 127.0.0.1:22. Поэтому ядро ответит TCP RST, а клиент увидит «Connection refused».
«Главнее» здесь не одно, а оба условия сразу. Чтобы соединение состоялось, нужно, чтобы firewall пропустил пакет и чтобы на этом адресе был слушающий сокет. Firewall может только запретить. Открыть то, что никто не слушает, он не может. Поэтому побеждает более узкое ограничение, в нашем случае привязка к адресу.
Правило ACCEPT для 22 сейчас просто ничего не делает. Но стоит кому-то поменять ListenAddress на 0.0.0.0, и SSH сразу станет доступен снаружи.
2. Чего не хватает web42ns для выхода в интернет
Маршрута по умолчанию внутри namespace. Сейчас namespace знает только свою подсеть veth. Нужна команда ip netns exec web42ns ip route add default via 10.200.0.1, то есть шлюзом становится хостовый конец veth.
Форвардинга на хосте. Нужно net.ipv4.ip_forward=1. Без него хост не передаёт пакеты между veth и eth0. Это та самая цепочка FORWARD, и если её политика DROP, пакеты нужно в ней явно разрешить.
SNAT/MASQUERADE в POSTROUTING, например -t nat -A POSTROUTING -s 10.200.0.0/24 -o eth0 -j MASQUERADE.
Для работы по именам ещё понадобится DNS (/etc/netns/web42ns/resolv.conf).
Зачем нужен MASQUERADE. Адрес 10.200.0.2 приватный. Если пакет уйдёт с ним как есть, провайдер его скорее всего отбросит. А если не отбросит, ответ всё равно не вернётся: маршрута к 10.x в интернете нет. MASQUERADE на выходе подменяет адрес источника на 203.0.113.10. Conntrack запоминает эту подмену, и когда приходит ответ, адрес назначения автоматически меняется обратно на 10.200.0.2. Docker делает для 172.17.0.0/16 ровно то же самое.
3. Почему ни INPUT, ни ufw не закрывают 8080
Ключ в порядке обработки пакета:
-p 8080:8080 создаёт DNAT-правило в nat/PREROUTING (цепочка DOCKER): 203.0.113.10:8080 → 172.17.0.2:8080.
PREROUTING срабатывает до решения о маршруте. Поэтому, когда ядро спрашивает «это мне?», адрес назначения уже 172.17.0.2. Ответ «не мне», и пакет идёт в FORWARD, а не в INPUT.
INPUT с его политикой DROP и правилами ufw (а ufw по умолчанию правит именно INPUT) этот пакет просто не видят. В FORWARD же Docker сам добавил ACCEPT для своего контейнера.
Как закрыть порт правильно:
привязать проброс к localhost: -p 127.0.0.1:8080:8080;
или добавить правила в цепочку DOCKER-USER, она проверяется в FORWARD раньше правил Docker;
или использовать ufw route deny.
4. Прямой порт 8080 против nginx на 80
В варианте (а) сломается или станет неудобным следующее:
TLS-терминация. HTTPS придётся делать в самом приложении, то есть возиться с сертификатами и их продлением внутри web-42. Иначе приложение останется на голом HTTP, и пароли будут ходить в открытом виде.
Одна точка входа. Каждый новый сервис потребует ещё одной дыры в firewall, и поверхность атаки растёт. Пользователи должны помнить :8080, а корпоративные сети и публичный Wi-Fi часто блокируют нестандартные порты.
Роутинг по домену. Не получится раздавать web42.example.com, shop.example.com и api.example.com через один 80/443. Всё сводится к «IP + номер порта».
Балансировка. Нельзя поставить несколько копий web-42 за одним адресом. Перезапуск или деплой означает простой, а нагрузка не распределяется.
